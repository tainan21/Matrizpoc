## 1. Objetivo desta fase

Esta fase **não** existe para completar profundamente o banco de todos
os apps. Ela existe para:

- tornar o **Core** a camada real de identidade/autenticação do ecossistema;
- tornar o **Hub** a camada real de persistência institucional;
- instalar **auth real cross-app** (com identity linking correto);
- persistir **telemetry / health / readiness**;
- provar **1 resource MCP + 1 tool MCP** reais contra o Hub;
- manter `Seumei` e `Contracts` como provas reais **mínimas**;
- preservar L1–L12 e a preparação para extração futura de cada app.

Fora de escopo, explicitamente (ver §9):
Spot profundo, WillDash profundo, wallet/coins, engine financeira,
cross-schema FK entre apps, MCP amplo, hiper-normalização do Hub.

## 3. Diagnóstico técnico de gaps

### 3.1 Gaps críticos no Core

| Gap | Evidência | Impacto |
|---|---|---|
| **`User` não é global** | `model User { tenantId String; tenant Tenant @relation(...) }` | Impossível ter identidade cross-app/cross-tenant. Viola decisão declarada ("User → identidade global"). |
| **Sem `AuthAccount`** | Auth só em memória; nenhum modelo representa provider+subject | Sem auth real persistível. |
| **Sem `AuthVerificationChallenge`** | OTP/magic-link são `Map` em RAM dentro do processo | Rebooting server invalida toda tentativa em voo. |
| **`SharedSession` é placeholder** | Comentário do schema: "not strictly required in V1" | Sessão real server-side não existe. |
| **Sem mecanismo de identity linking** | Não há modelo que una "Alice@spot" e "Alice@seumei" na mesma `User` global | Usuário entrando num segundo app duplica. |
| **`Membership.role` só tem enum pequeno** | `OWNER / ADMIN / MEMBER / VIEWER` | Aceitável para fase atual; não bloqueia. |
| **`TelemetryRecord` existe mas ninguém grava** | Nenhum gateway persistindo envelopes | Categorias V1.2 não sobrevivem reload. |

### 3.2 Gaps críticos no Hub

| Gap | Evidência | Impacto |
|---|---|---|
| **Sem schema próprio** | Não existe `hub.prisma` | Registry volátil. Refresh perde histórico. |
| **`IngestionPipelineRun` não persiste** | `let cached: InstitutionalBootstrapReport` | Impossível auditar ingestions passadas. |
| **Health / readiness / public metrics não persistem** | Só vivem no `ProjectManifest` agregado em RAM | `/public` e `/health` reconstroem tudo a cada boot. |
| **Fonte externa é JSON local estático** | `seeds/matriz-ventures-registry.json` | Esperado (L3/L12), mas precisa registro persistido da última "versão importada". |

### 3.3 Gaps nos apps de prova (Seumei, Contracts)

| Gap | Evidência | Impacto |
|---|---|---|
| **Repositórios são mock `localStorage`** | `src/mock/repositories.ts` | Nada persiste de verdade. |
| **Nenhum Prisma client instanciado** | Só `prisma validate`, nunca `prisma generate` rodou para produção | Ainda não dá para testar escrita real. |
| **Contracts não grava ExternalLink de origem** | `Contract.originApp/originEntityType/originEntityId` existe como colunas livres; não usa a tabela `ExternalLink` em core | Duplicidade conceitual entre "origem" inline e "link cross-app". |

### 3.4 Gaps transversais

| Gap | Impacto |
|---|---|
| **Sem estratégia de 1 Postgres físico × N schemas lógicos documentada** | O `.env.example` usa 5 URLs distintas (um DB por app). A decisão desta fase é o oposto: **1 instância, vários schemas**. Precisa convergir. |
| **Nenhum cliente Prisma gerado/reutilizado** | Não há `packages/platform/prisma-clients` nem helper compartilhado. |
| **Auth strategies não falam com o Core** | Verify/start resolvem identidade localmente em RAM. |
| **L3 precisa ser reafirmada**: apps não devem importar `@prisma/core/*` cruzado. Toda leitura de identidade/sessão passa por **contrato** (HTTP/`SessionService`), não por Prisma client compartilhado. |

## 4. Proposta de modelagem (Fase 1–2)

Todos os deltas abaixo são **proposta**. Nenhum foi aplicado ainda.

### 4.1 Estratégia de banco físico vs. lógico

Decisão assumida do prompt: **1 Postgres físico + schemas lógicos por app**.

Convergência concreta:

- Em **runtime** (dev/preview/prod), todas as URLs apontam para a mesma
  instância, com `?schema=<app>` diferente:
  ```
  CORE_DATABASE_URL=postgresql://.../matriz?schema=core
  HUB_DATABASE_URL=postgresql://.../matriz?schema=hub
  SEUMEI_DATABASE_URL=postgresql://.../matriz?schema=seumei
  CONTRACTS_DATABASE_URL=postgresql://.../matriz?schema=contracts
  SPOT_DATABASE_URL=postgresql://.../matriz?schema=spot
  WILLDASH_DATABASE_URL=postgresql://.../matriz?schema=willdash
  ```
- **Schema por arquivo** (L1) é mantido; cada arquivo gera um client
  próprio em `node_modules/.prisma/<app>`.
- **Não criamos cross-schema FK**. Referências cross-schema continuam
  via `ExternalLink` no Core (L3).
- Extração futura (um app para seu repo próprio) só precisa apontar o
  `<APP>_DATABASE_URL` para uma instância separada — **zero mudança de
  código**.

### 4.2 `core.prisma` — deltas

**Manter**: `Tenant`, `Membership`, `AppRegistration`, `ExternalLink`,
`OnboardingProgress`, `TelemetryRecord`.

**Ajustar**:

- `User` → identidade global:
  - remover `tenantId` e a relação `tenant` em `User`
  - pertencimento a tenants passa a ser **exclusivamente** via `Membership`
  - manter `email @unique` como chave de identity linking inicial
  - adicionar `locale String?`, `timezone String?` para preparar cross-app UI

- `Membership` mantém shape; passa a ser **a única** ponte user↔tenant↔app.
  - confirmar `@@unique([tenantId, userId, appId])` (já existe)
  - adicionar `invitedAt DateTime?`, `lastActiveAt DateTime?` (soft)

- `SharedSession` → renomear para `AppSession` e ganhar corpo real
  (ver §4.3).

**Adicionar** (auth real):

- `AuthAccount` — provider×subject para um `User`:
  ```
  id           cuid
  userId       -> User.id
  provider     enum(MAGIC_LINK, OTP, OAUTH_GOOGLE, OAUTH_GITHUB, PASSWORD)
  providerSubject String  // hash(email), oauth sub id, etc.
  email        String?
  emailVerifiedAt DateTime?
  metadata     Json?      // detalhes específicos do provider
  createdAt    DateTime
  updatedAt    DateTime
  @@unique([provider, providerSubject])
  @@index([userId])
  ```
  Este modelo é o ponto de **identity linking**: dois sign-ins com o
  mesmo `email` e provider diferente podem apontar para o mesmo `userId`.

- `AuthVerificationChallenge` — OTP / magic-link persistíveis:
  ```
  id           cuid
  kind         enum(OTP, MAGIC_LINK)
  email        String
  codeHash     String     // OTP hash ou token hash
  attempts     Int @default(0)
  maxAttempts  Int @default(5)
  expiresAt    DateTime
  consumedAt   DateTime?
  createdAt    DateTime
  ipHash       String?
  userAgent    String?
  @@index([email, kind])
  @@index([expiresAt])
  ```

- `AppSession` (ex-SharedSession) — sessão real server-side:
  ```
  id             cuid
  userId         -> User.id
  tenantId       -> Tenant.id
  appId          String                 // app onde a sessão foi emitida
  strategyId     String                 // magic-link | otp | ...
  tokenHash      String @unique         // SHA-256 do session token
  issuedAt       DateTime
  expiresAt      DateTime
  revokedAt      DateTime?
  lastSeenAt     DateTime
  ipHash         String?
  userAgent      String?
  @@index([userId])
  @@index([tenantId, appId])
  @@index([expiresAt])
  ```
  - cookie HTTP-only no browser carrega o token em claro; o DB só
    armazena o hash.
  - `appId` permite saber em qual app a sessão nasceu; permite auditoria
    cross-app sem cross-schema FK.

- Enum novo: `AuthProvider { MAGIC_LINK, OTP, OAUTH_GOOGLE, OAUTH_GITHUB, PASSWORD }`
- Enum novo: `AuthChallengeKind { OTP, MAGIC_LINK }`

**Preparar melhor `TelemetryRecord`** (não muda shape, mas vira
destino real):

- adicionar campo `category String?` (espelho de `InstitutionalTelemetryCategory`)
- adicionar `@@index([tenantId, category])` e `@@index([occurredAt, category])`
- manter `eventVersion` para L7

### 4.3 `hub.prisma` — novo arquivo

**Responsabilidade**: persistir o control plane institucional (não
domínio de app).

Modelos (primeira iteração):

- `InstitutionalProject`
  ```

  projectId          String @unique   // ex: "matriz:hub", "matriz:ventures-registry"

  metadata     Json?
  createdAt    DateTime
  updatedAt    DateTime
  ```

- `InstitutionalIngestionRun`

  sourceId     -> InstitutionalSource.id
  startedAt    DateTime
  finishedAt   DateTime
  durationMs   Int
  accepted     Int
  rejected     Int
  errorsJson   Json?
  reportJson   Json              // IngestionPipelineRun completo

## 5. Auth real cross-app — modelo proposto

### 5.1 Fluxo: primeiro login de usuário novo

```
[Spot] login form
  └─ POST /auth/otp/start (app Spot)
      └─ SessionService (core-backed) cria AuthVerificationChallenge
[Spot] UI pede código
  └─ POST /auth/otp/verify
      └─ SessionService valida challenge
         ├─ localiza User por email (não encontra)
         ├─ cria User global
         ├─ cria AuthAccount (provider=OTP, subject=email)
         ├─ cria Tenant default se aplicável (ou usa existente do convite)
         ├─ cria Membership(tenantId, userId, appId=spot)
         ├─ cria AppSession (tokenHash, appId=spot)
         └─ set cookie http-only
      └─ retorna AuthSession (formato v1 já existente)
```

### 5.2 Fluxo: usuário já existe em outro app

```
[Seumei] login (OTP)
  └─ verify OTP
      └─ SessionService:
         ├─ localiza User por email (existe, veio do Spot)
         ├─ AuthAccount já existe? se não, cria nova (provider=OTP, mesmo userId)
         ├─ Membership(tenantId, userId, appId=seumei) existe? senão cria
         ├─ cria AppSession (tokenHash, appId=seumei)
      └─ zero duplicação de User
```

### 5.3 Identity linking — critérios

- **Chave primária de linking**: `email` normalizado (`lower + trim`).
- Extensões futuras (fora desta fase): OAuth `sub`, telefone, etc.
- Um mesmo `User` pode ter múltiplos `AuthAccount` (um por provider).

### 5.4 Contratos tocados

Auth V1 (`packages/platform/auth/src/v1`) **não muda o tipo
`AuthSession`** (L7). Muda apenas a implementação por trás das
estratégias: de in-memory `Map` para chamadas a um `SessionService`
que fala com `core.prisma`. Storage client-side continua como snapshot
do que o server já persistiu.

### 5.5 Onde o código mora

- `packages/platform/auth` — **mantém sua forma**. Vira orquestrador.
- Implementação real é injetada via **strategies e um novo
  `ServerSessionAdapter`**; o client continua consumindo o mesmo
  `AuthProvider`.
- O "server" concreto do auth vive no app que hospeda a rota
  (Next.js Route Handlers em cada app), mas todos apontam para um
  `@matriz/platform-auth-server` que conversa com o Core via cliente
  Prisma dedicado.
- **L12** preservada: `platform-auth-server` sabe de identidade, não
  conhece gig/establishment/contract/goal.

## 6. MCP real — resource e tool concretas

Escopo desta fase: **1 resource + 1 tool**, rodando contra o Hub
persistido.

- **Resource**: `matriz://projects/{projectId}`
  - retorna `ProjectManifest` completo lido de
    `InstitutionalProject.manifestJson` mais último `health` e
    `publicMetrics` snapshots.
  - encoding: JSON; mime `application/json`.
- **Tool**: `refresh_project_ingestion`
  - input: `{ sourceId?: string }` (opcional; sem ela, refresha tudo).
  - efeito: invoca `runInstitutionalIngestion()` já existente no Hub,
    mas agora persistindo `InstitutionalIngestionRun`.
  - saída: `{ accepted, rejected, durationMs, replacedAt }`.

Hospedagem inicial: rota Next.js do próprio Hub
(`apps/matriz-hub/app/api/mcp/route.ts`) implementando o SDK
`@modelcontextprotocol/sdk` em modo HTTP/stdio (decisão na Fase 6 —
ver §7).

Governança permanece alinhada com [mcp-capabilities-model.md](../mcp-capabilities-model.md)
— nenhum contract muda; apenas deixa de ser declarativo e passa a
responder de verdade.

- A cada `runInstitutionalIngestion()` bem-sucedida:
  - cria `InstitutionalIngestionRun` com `reportJson`
  - faz upsert em `InstitutionalProject` por projeto
  - opcionalmente cria `InstitutionalHealthSnapshot` e
    `InstitutionalPublicMetricsSnapshot` por projeto
- `/health`, `/ecosystem`, `/public` passam a ler do banco, com cache
  curto em processo para não martelar Postgres a cada render.

Nada disso exige inflar domínio; são apenas tabelas de snapshot
append-only.

## 11. Perguntas abertas antes de implementar

Respostas a estas perguntas travam o design da Fase 1 em diante. Seguem
como as únicas decisões que o plano ainda deixa em aberto:

1. **Localização do cliente Prisma**: criar
   `packages/platform/prisma-clients` (um client singleton por schema,
   reutilizável por qualquer app) ou manter `src/integration/prisma/client.ts`
   **por app** (máxima autonomia, um pouco mais de boilerplate)?
   Minha recomendação: **por app**, preservando L3 (apps não compartilham
   client do Core; falam com Core só via `SessionService`).

2. **Um único banco físico em dev**: confirmar se o plano é rodar
   `docker compose` (ou Vercel Postgres / Neon serverless) com uma única
   instância Postgres, schemas `core/hub/seumei/contracts/spot/willdash`,
   usuário único. Isso simplifica `.env.example` para 1 URL base + 1
   variável de schema por app.

3. **Provider principal de auth desta fase**: OTP e Magic Link (que
   já existem como mock). OAuth fica declarado em enum mas sem
   implementação? (minha recomendação: sim, ficam enum-only para não
   expandir escopo.)

4. **Identity linking automático por email vs. com confirmação**: na
   primeira prova, assumir que `email` é suficiente para unificar (sem
   fluxo de "você já tem conta — confirma vinculação?"). Se sim, a Fase
   5 fica simples; se não, vira Fase 5b.
